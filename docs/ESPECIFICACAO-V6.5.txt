## Camada B — Podman rootless

Utilizar contêineres apenas quando trouxerem vantagens técnicas.

Aplicações previstas:

- Ferramentas leves do Kali.
- Auditoria de aplicações autorizadas.
- Ambientes descartáveis.
- Testes de integração.
- Workers auxiliares.
- Testes de dependências.

Requisitos:

1. Preferir rootless.
2. Utilizar imagens confiáveis.
3. Evitar contêineres privilegiados.
4. Controlar montagens do host.
5. Limitar CPU e memória.
6. Configurar redes adequadas.
7. Proteger segredos.
8. Não expor portas desnecessárias.
9. Registrar origem e versão das imagens.
10. Não tornar Podman obrigatório para o núcleo do Sentinel.

## Camada C — Kali Linux virtualizado

Utilizar QEMU/KVM, libvirt e virt-manager.

Aplicações:

- Pentests autorizados.
- Laboratórios Red Team.
- Exercícios Purple Team.
- Testes de sistemas completos.
- Experimentos que exigem kernel próprio.
- Redes virtuais isoladas.
- Pesquisas controladas.

A máquina virtual deverá permanecer desligada quando não estiver em uso.

Não utilizar contêineres ou chroot como substitutos de isolamento apropriado para experimentos perigosos.

# 8. DIRETRIZ OFICIAL — FIREBASE, SUPABASE E SERVIÇOS EXTERNOS

**Esta seção é obrigatória e substitui qualquer interpretação anterior de que Firebase e Supabase seriam dependências internas do I.See Sentinel.**

O I.See Sentinel não utilizará Firebase ou Supabase como infraestrutura obrigatória.

O sistema manterá backend próprio, banco PostgreSQL e gerenciamento independente de autenticação, eventos, incidentes, evidências e relatórios.

Firebase e Supabase serão tratados exclusivamente como tecnologias de aplicações externas que poderão ser submetidas a auditorias autorizadas.

## 8.1 Firebase

O Sentinel SecureBuild deverá futuramente permitir auditoria de projetos que utilizam Firebase.

Verificações previstas:

- Regras do Firestore.
- Regras do Realtime Database.
- Permissões do Cloud Storage.
- Configurações de autenticação.
- Controles de acesso.
- Exposição de credenciais.
- Uso indevido de credenciais administrativas.
- Configurações inseguras.
- Separação de dados entre usuários.
- Integrações inseguras com serviços externos.

Diferenciar configurações públicas legítimas de segredos administrativos efetivamente sensíveis.

As auditorias deverão ocorrer por análise de código e configurações fornecidas ou acesso explicitamente autorizado.

## 8.2 Supabase

O Sentinel SecureBuild deverá futuramente permitir auditoria de projetos que utilizam Supabase.

Verificações previstas:

- Row Level Security (RLS).
- Políticas de acesso.
- Separação de dados entre usuários.
- Permissões PostgreSQL.
- Configurações de autenticação.
- Políticas de armazenamento.
- Edge Functions.
- Exposição de service-role keys.
- Segredos em código-fonte.
- Configuração de APIs.
- Falhas de autorização.
- Configurações inseguras.

Não considerar chaves públicas de cliente automaticamente vulnerabilidades.

Os achados deverão ser classificados conforme o risco real e as permissões efetivamente disponíveis.

## 8.3 Adaptadores externos

Criar futuramente uma camada chamada:

**Sentinel SecureBuild — External Backend Security Adapters.**

Ela poderá incluir:

- Firebase Security Adapter.
- Supabase Security Adapter.
- AWS Security Adapter.
- Azure Security Adapter.
- Google Cloud Security Adapter.
- PostgreSQL Security Adapter.
- MySQL Security Adapter.
- Outros conectores tecnicamente justificados.

Cada adaptador deverá:

1. Possuir contrato de interface documentado.
2. Operar com acesso mínimo.
3. Priorizar leitura.
4. Respeitar o escopo autorizado.
5. Proteger credenciais.
6. Não armazenar segredos desnecessariamente.
7. Produzir achados verificáveis.
8. Classificar riscos.
9. Preservar evidências pertinentes.
10. Gerar recomendações.
11. Integrar-se ao RiskGraph.
12. Integrar-se ao SecureFix.
13. Registrar todas as ações.

## 8.4 Prioridade de desenvolvimento

Firebase e Supabase não serão prioridades da primeira implementação.

Primeiro desenvolver:

1. Núcleo do Sentinel.
2. SecureBuild genérico.
3. Auditoria estática de código.
4. Análise de dependências.
5. Detecção de segredos expostos.
6. Auditoria de autenticação e autorização.
7. Avaliação de APIs.
8. Relatórios de segurança.

Após validação dessas capacidades, implementar adaptadores externos conforme demanda.

**Regra final:** o Sentinel deverá conseguir auditar sistemas que utilizem Firebase ou Supabase sem depender dessas plataformas para sua própria operação.

1. Preservar todos os módulos.
2. Priorizar o Debian como estação principal.
3. Desenvolver o núcleo de forma independente.
4. Utilizar PostgreSQL local.
5. Não utilizar Firebase como backend interno.
6. Não utilizar Supabase como backend interno.
7. Tratar Firebase e Supabase somente como tecnologias externas auditáveis.
8. Não exigir APIs pagas.
9. Não exigir Docker ou Podman.
10. Usar Kali virtualizado quando necessário.
11. Preservar compatibilidade Windows/Linux.
12. Manter inicialmente apenas um operador.
13. Evitar complexidade comercial prematura.
14. Respeitar autorizações de segurança.
15. Proteger dados e segredos.
16. Respeitar licenças.
17. Desenvolver funcionalidades reais.
18. Executar testes.
19. Documentar resultados.
20. Não inventar evidências.
21. Não declarar módulos prontos sem validação.
22. Otimizar para o hardware disponível.
23. Preservar a futura expansão Enterprise.
